Design Annotations

✦
Iris CDS — Autotrader tokens & type
Every color, radius, spacing, type and component size flows from a token layer whose values are pulled from the Iris CDS Figma library — resolved in the Autotrader theme mode. Iris paths in use: comp/color/*button/primary & content/link (Autotrader blue #024aa5), base/color/neutral-*, feedback success·caution·error, comp/size/radius/* (chip = pill, message = 24, card/sheet = 8, button/input = 4), sem/space/*, and the Autotrader UI font Roboto with the Iris type scale (body 1.5, heading 1.2). Components are sized to Iris specs — button 48, chip 32, input 48.
1
Offer card — dual POV
Same offer card renders in both views. Buyer sees "Your Offer" with Rescind/Counter; Seller sees "Offer Received" with Decline/Counter/Accept.
Trade-off: Card needs to stay in sync — shared state object drives both
!
ID-verification gate
While the buyer is unverified they're on rails: canned request chips only, one question at a time, capped at a 5-question quota (then a verify wall). Questions retire once answered — each maps to a fact, so its chip drops once that fact is known. The seller can free-form message at will (verified listing owner), and also gets optional one-tap quick replies that post an answer directly into the thread. The buyer sees an "ID Verified" badge (mutual trust). Offers/test drives still need a verified buyer; the seller can nudge via "Ask Buyer to Verify". Demo both states with the BUYER ID toggle.
2
Buyer quick-action chips
Make Offer and Test Drive chips persist above input. Chips disable contextually (e.g. offer already accepted).
Alt: + icon expands action menu
3
Seller offer actions
Seller gets 3 actions inline: Decline (ghost), Counter (primary), Accept (green). Accepting triggers a confirmation sheet before committing.
Rationale: Friction before Accept prevents accidental commits
4
Connected state engine
Both frames share a single JS state object (offerState). Any action in one view immediately reflects in the other — no reload needed.
Trade-off: In prod this would be real-time via websocket/SSE
5
Accept → buyer notification
When seller accepts, buyer's offer card updates to "Accepted" state and a confirmation banner posts in the buyer chat thread automatically.
Rationale: Buyer needs clear real-time signal — not just badge change
6
View switcher (Both mode)
Desktop/tablet mode shows both frames side by side. State changes animate in both simultaneously, making the connected flow visible in demos.
Alt: Single frame with tab toggle only
7
Seller header context
Seller header shows buyer identity + offer count badge. Keeps seller anchored to who they're negotiating with without leaving chat.
Trade-off: Multiple buyers would need a conversation list above
